## The premise, challenged

Three rounds of "fix the video, resubmit" have cost ~4 weeks. The instinct after
this rejection is a fourth video. Before spending that, the question worth asking
is not "what was wrong with the video" but **"why do some permissions pass and
others fail on the same video?"**

## The hypothesis that is FALSIFIED

"Meta will not grant write permissions to this app."

`instagram_business_manage_comments` is a write permission -- it creates comments
on someone's account -- and it was approved this round. So the split is not
read vs write.

## What the approved and rejected demos actually differ on

The Instagram comments segment (2:13-3:45 of the IG video) is one continuous,
uninterrupted causal chain on a single platform: a visitor comments -> Gituas
reads it -> the owner types a reply -> sends -> the reply appears on
instagram.com. Cause and effect adjacent in time. Approved.

The Facebook video's `pages_manage_posts` story is split across the runtime:
approve at 2:02, then ~65 seconds of unrelated engagement material, then the
post on facebook.com at 3:07. A reviewer checking "did they demonstrate creating
a Page post end to end" has to *infer* that the post at 3:07 is the one approved
at 2:02. Rejected.

`pages_manage_engagement` has the same shape -- reply typed at 2:40, proof at
3:49. Rejected.

**We uploaded the same 4-minute file against four different permissions.** Meta
accepts a different screencast per permission; we gave every reviewer the same
video and asked each of them to find their permission inside it.

## Two hard facts found in the dashboard today

1. **A dependency we never satisfied.** The `pages_manage_posts` dialog states:
   > "Your submission must include pages_show_list **and pages_read_engagement**
   > to use pages_manage_posts"

   `pages_read_engagement` is itself rejected, so `pages_manage_posts` cannot be
   granted until it passes. They must be fixed together, in that order.

2. **`pages_read_engagement` was demonstrated on an empty screen.** Meta returns
   no insights for a Page this small, so the engagement card in the video reads
   "no insights available yet". We asked for a permission to read Page content
   and insights, and showed a panel with no data in it.

3. **An unresolved required action: `Submit Data Use Checkup`** (Action ID
   1741202236995542), sitting on the app through all three submissions.
   > "You must resolve the issues below to retain access to Meta APIs. If you do
   > not respond, access will be restricted."

   Unknown whether it influences review outcomes; known to be a standing
   compliance flag on the account while reviewers look at it.

## Reviewer's own words

Beyond the Developer Policy 1.6 boilerplate, the `pages_manage_posts` dialog
carries a human note:
> "SC failed to demonstrate its requested use case"

SC = screencast. It is the video, not the written use case -- Meta states
explicitly "We have determined that your apps' use case is allowed".

## What this implies

Stop making one video for many permissions. Make one short, self-contained video
per permission: consent -> the single action -> the result on the platform, in
one unbroken take, 60-90 seconds. That is the shape of the three that passed.

And fix `pages_read_engagement` first, because `pages_manage_posts` is blocked
behind it -- which means demonstrating it on a Page that actually returns data,
or demonstrating the parts of it that do work (reading the Page's own posts)
rather than an empty insights panel.

## Open question this review did NOT answer

The reviewer notes for `pages_manage_engagement`, `pages_read_engagement` and
`instagram_business_content_publish` were not read -- the dashboard reset each
time they were added to the draft. They may say something different from
`pages_manage_posts`. Worth reading before committing to the plan above.
